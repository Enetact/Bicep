# Private Managed DevOps Pool module

Creates one `Microsoft.DevOpsInfrastructure/pools@2026-06-02` resource, using the current stable [ARM resource contract](https://learn.microsoft.com/en-us/azure/templates/microsoft.devopsinfrastructure/2026-06-02/pools). The source was checked against Bicep MCP schema metadata and Microsoft Learn. It is a workload-specific native module; it does not claim AVM certification or generic source-draft eligibility.

The module references an existing Dev Center project and an exclusive, predelegated subnet. It does not create shared network resources, role assignments, Dev Center foundations or credentials. It declares pool administrator groups and project access; external Azure DevOps organization memberships, creation/update privileges, pipeline authorization and service connections remain separately administered. Platform onboarding must qualify the DevOpsInfrastructure service principal's VNet permissions and same-region subnet requirements before deployment. See [Managed DevOps Pools networking](https://learn.microsoft.com/en-us/azure/devops/managed-devops-pools/configure-networking?view=azure-devops).

The baseline is stateless service-mode agents with standby disabled: both `resourcePredictionsProfile` and `resourcePredictions` are omitted, following Microsoft's [scaling guidance](https://learn.microsoft.com/en-us/azure/devops/managed-devops-pools/configure-scaling?view=azure-devops). Maximum concurrency defaults to two (bounded one to ten), with Standard SSD OS storage and no additional disks. The pool/agents receive no managed identity or ambient Azure rights. Jobs use separately reviewed WIF service connections. Azure storage encryption remains platform-managed; no customer-managed key or host-encryption setting is claimed by this interface.

One pinned Windows Server 2022 Gen2 Azure Pipelines image is configured. `agentImageVersion` must identify a reviewed published version; no actual release identifier is invented in the environment examples. The workflow rejects `latest` and incomplete pins. The [image guidance](https://learn.microsoft.com/en-us/azure/devops/managed-devops-pools/configure-images?view=azure-devops) recommends Gen2 images; the selected v5 VM profiles also avoid current Azure Pipelines image restrictions on v6/v7 hardware. Regional quota and capacity still require live qualification.

Azure resource names and organization pool aliases are separate inputs. The module creates the alias only in the explicit project list, sets `openAccess: false`, and assigns pool administrators through reviewed security-group email addresses with `SpecificAccounts`. Per-pipeline authorization, protected environments and creation/update privileges remain Azure DevOps administration work. See [pool security](https://learn.microsoft.com/en-us/azure/devops/managed-devops-pools/configure-security?view=azure-devops).

Use the [workload guide](../../../workloads/managed-devops-pool/README.md) for the full standard flow, bootstrap-runner separation, defaults, costs, evidence and acceptance. Creating the pool does not prove agent provisioning, private DNS/reachability, Azure DevOps scheduling or Fabric private release acceptance.
