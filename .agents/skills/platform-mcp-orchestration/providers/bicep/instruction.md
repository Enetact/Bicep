# Bicep decisions

Provider id: `bicep`. Begin with best practices, resource/extension type discovery and the exact API-version schema. Check well-known extensions and Azure Verified Module metadata before drafting a module interface. Metadata does not supply missing business inputs or establish deployment readiness.

For existing source, inspect file references, then choose Bicep/parameter compilation, formatting, an existing-deployment snapshot or ARM template/parameter decompilation as requested. Distinguish source transformation, compiler success, observed Azure configuration and actual deployment. Never treat a snapshot or compilation as What-If, approval or runtime acceptance.

Use absolute repository source paths in discovered `filePath` arguments. Compilation/format/reference/snapshot calls check native file references before and after execution, including modules, loaded data and configuration. Protected paths, outside-repository dependencies, links and unverifiable references block the call. The guard is bounded to 256 compilations, 2,048 files and 45 seconds; it is not an OS sandbox. JSON decompile has direct-path checks only. Source-writing tools need an exact plan; preserve unrelated edits and inspect resulting diffs.

Schema/module/public guidance calls need no Azure grant. Resource-backed snapshots use the connected isolated Azure CLI cache; registered-app-only sign-in does not supply that cache. Reconnect Bicep after changing Microsoft identity. A visible resource needs its actual read authorization; never substitute another account or default cache.

If a module reference is outside permitted source, report that dependency instead of copying it into an allowed path to evade policy. For invalid source or unresolved parameters, report the specific missing inputs and propose a reviewed source correction; do not deploy to discover defaults.

## Adopt a reviewed AVM capability

For requested module expansion, research with `get_bicep_best_practices`, `list_avm_metadata`, Learn and the selected official GitHub source. If the full metadata result is withheld by the output budget, record that limit and use focused official module/release documentation; do not encode or replay withheld output. Resolve the exact published version, immutable source commit and registry manifest/template digest before adoption. Child modules are often packaged inside the parent release; never invent an independently published child registry path.

The application's reviewed AVM wrappers live under `modules/avm/`, with a separate `config/avm-module-contracts.json`. They reference exact local official compiled ARM artifacts under `vendor/azure-verified-modules/`, preserving full inline child templates and MIT provenance. `Verify-AvmSources.ps1` and `Update-BicepModuleContracts.ps1 -Check` validate the release bytes and complete dependency closure. The updated draft emitter packages that closure with the source; arbitrary imports, registry restores, external template links and executable hooks remain unsupported. The legacy catalog is retained separately so an older signed-in binary can continue serving its existing modules until governed activation.

Choose only wrappers actually present in the frozen draft context. Expose reviewed names, location, tags, constrained SKU/retention profiles and sealed typed child arrays; optional children default to empty. Keep private access, Entra authentication and telemetry choices explicit. Resource-type inventories include possible upstream conditional resources; they do not prove that every child is exposed or enabled by the wrapper. Preserve existing workload compositions and resource ownership. New AVM source features do not create registered deployable products or authorize changes to shared networks.

Identity federation requires reviewed issuer/subject/audience trust; NSG rules and routes require effective-network review. ACR and App Configuration need qualified private endpoints/DNS and access grants. Application Insights needs workspace and Azure Monitor Private Link qualification. Non-secret App Configuration key-value writes require data-plane write RBAC plus the documented ARM Private Link/pass-through deployment path. Keep credentials out of all parameter values. Report missing private connectivity, identity, ownership, region/SKU, cost and pipeline checks as gaps rather than weakening defaults.
