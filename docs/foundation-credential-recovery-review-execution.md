# Durable execution of an inactive credential recovery review

`FoundationCredentialRecoveryStageReviewCoordinator` explicitly composes one current foundation store with the concrete [completed-stage verifier](foundation-credential-recovery-stage-verification.md). It pins the store's database instance and the exact reviewed stage plan and completion receipt. This local C# API records customer-scoped evidence that an already completed, held stage was authenticated. It does not recover a live key, adopt a vault, activate a cell, dispatch a pipeline, or authorize promotion. No HTTP, MCP, model, worker, or default host route selects it.

The [review contract](foundation-credential-recovery-review.md) requires a nonempty set of source profiles and no absent-profile entries. Every unique project/environment represented by those profiles needs its own current `CustomerContext`. Request, approval, execution and reading use the existing `CredentialRecoveryPrepare`, `CredentialRecoveryApprove`, `CredentialRecoveryVerify` and `CredentialRecoveryRead` capabilities. Each supplied set must cover exactly the required scopes with one human actor, one current actor version and the required signed and standing roles. Workload identities and support grants cannot supply this authority. The approver must differ from the requester and executor.

Preparation checks current database authority before opening private stage files. It holds the stage's concrete read guard, checks the full bounded tree, owner-only custody, plan and receipt pins, historical completion time, preserved profile hashes and source metadata, then persists the scoped review and audit events. Preparation and approval do not resolve the destination key. A new review expires within 15 minutes and within its requester's context lifetime; approval also pins the approver's context expiry. The original source set and stage plan may now be expired: they remain historical evidence, while this new review requires fresh authority.

Execution follows these boundaries:

1. Copy the supplied executor contexts and check their current scope authority, review digest, policy, database instance and exact target. Open the real stage read guard and validate metadata before destination-key access.
2. In a short SQLite transaction, recheck activation, lifecycle, all scoped contexts, original requester and approver standing grants and versions, policy, instance and review expiry. Commit one admission and its scoped audit events with execution state `OutcomeUnknown`. This claim is consumed before any destination-key read.
3. Keep the same read guard while resolving the independently pinned destination key once. Recheck the full tree after that external await, authenticate all retained encrypted profile bytes with the frozen key, and compare the exact preserved profile and dependency hashes. The current source vault and source key provider are not consulted.
4. Recheck the full stage again, then complete in a separate short SQLite transaction while the guard remains held. Completion revalidates the original executor contexts, their expiry and actor version, requester and approver standing grants and pinned expiry, lifecycle, policy, instance, activation and review expiry. No database transaction spans a key-provider await.

Successful execution is `Succeeded` with a typed `HeldStageVerified` result and scoped audit events. The result binds the review, target, actual stage-verification digest, plan, receipt, source set and observation time. The stage remains inactive and held. `PromotionAuthorized`, `LiveAdoptionAuthorized`, `ActivationPerformed` and `ExternalExecutionAuthorized` are false. Durable authorization by distinct human principals is local evidence; it does not attest human presence or independent organizational or host custody. The receipt supplies no independent backup coverage, key retirement permission, production recovery acceptance, or protection from a privileged owner replacing both evidence roots.

Cancellation, key failure, stage changes, revoked or expired authority, process termination, or completion-audit failure after admission keep the one-use admission consumed as `OutcomeUnknown`. A definite successful database commit can also be ambiguous to a caller if the response is lost. Read the scoped durable history; do not retry the consumed request, infer no effect from an exception, or turn this record into activation authority. `RecoveryStageReviewAdmissionUncertain` means an admission commit was attempted and its outcome is uncertain, rather than a definite pre-admission refusal. The coordinator records only bounded public reason codes and keeps the stage guard through its outcome-audit attempt. It does not repair files or alter the stage.

The default operation deadline is 20 seconds with cooperative cancellation; trusted composition may choose another bounded deadline. An uncooperative key provider can retain both the awaiting operation and the stage guard beyond cancellation until it actually returns. The coordinator does not detach that operation or report success after cancellation. Public `CredentialRecoveryStageVerifier.VerifyAsync` remains available for the earlier trusted-owner read-only workflow and reuses the same internal held verification implementation; it does not acquire durable review authority on its own.

The native Windows synthetic execution tests exercise all-scope success, no key reads before admission, current authority changes during key waits and after AES verification, unchanged stage and key bytes, failed completion and outcome audits, caller-context list replacement, cancellation, cooperative deadlines, retained uncooperative providers, concurrent attempts and owned-process termination at both admission and verification checkpoints. The existing completed-stage verifier tests qualify the refactored public wrapper separately. Same-owner or administrator interference, trusted higher ancestors, continuous tamper detection, actual customer keys, live deployment and service-account recovery remain outside this local evidence.
