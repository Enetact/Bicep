# Stage the currently accepted credential recovery set

`CredentialRecoveryCheckpointStageExecutor` composes the concrete credential-set checkpoint authority with the existing [inactive staging executor](foundation-credential-recovery-staging.md). It supplies the missing durable latest-set constraint: a still-valid historical set and its own matching exact-set authority can no longer replace the current configured checkpoint in this workflow. This is explicit trusted-owner C# composition, with no new HTTP, MCP, AHP, model, worker or Owner CLI route.

The [checkpoint directory](foundation-credential-recovery-checkpoints.md) is provisioned separately and configured for one exact customer, cell, source vault namespace and public signer. Its identity commitment also binds its protected local custody. Retain the reviewed authority identity independently of an incoming private set. The set contains encrypted credential values together with private, unencrypted scope and original custody metadata; it is not a wholly encrypted export. The authority's local header also contains private custody metadata. Public checkpoint results contain commitments and never supply an encryption key or a private signing key.

```csharp
var staging = new CredentialRecoveryCheckpointStageExecutor(
    configuredCheckpointAuthority, independentlyReviewedAuthorityIdentity,
    new CredentialRecoveryStageExecutor(sourceKeys, destinationKeys, clock));

var result = await staging.StageLatestAsync(
    selectedPrivateSet, reviewedStagingPlan, reviewedPlanSha256,
    independentlyPinnedPublicSigner, reviewedCheckpointSequence,
    reviewedCheckpointSha256, cancellationToken);
```

The caller supplies the expected current checkpoint sequence and digest from its reviewed local selection. The wrapper acquires an actual shared read lease from the configured authority and requires that exact head. It checks the complete pinned authority identity, source namespace, selected set authority, exact private artifact digest, inventory digest and configured signer before any source or destination key access or output reservation. It freezes a public-only copy of the caller's signer; the inner executor still verifies the actual signed retained set and its current validity.

The same checkpoint lease remains held across every inner asynchronous key lookup, retained-byte authentication, destination-key commitment check, fresh private root reservation, stage output write and verification, and the final checkpoint recheck. A cooperating checkpoint append receives `CredentialRecoveryCheckpointBusy` while that lease is held. It can succeed only after the staging operation actually releases the lease. A snapshot of the head or a caller-created latest-authority DTO cannot substitute for this held operation.

Source and destination keys remain distinct inputs. Checkpoint acceptance authenticates all retained source ciphertext using the supplied source key provider; staging repeats its existing retained-set authentication and uses its separately pinned destination key. Neither operation reads the current live source vault or source rollback directory. They may be unavailable after capture without replacing the selected artifact, namespace, available source keys or checkpoint requirements. This is not evidence that a source host has been fenced.

The wrapper preserves the existing staging rules. It creates one fresh owner-private held root, refuses existing or unsafe destinations, preserves each original profile's complete scope, generation, expiry, enabled flag and kind, and writes stage-only namespace and high-water metadata. Empty sets and committed absence maps remain supported by this trusted-owner staging API. The later [customer-scoped durable review](foundation-credential-recovery-review.md) still refuses empty profiles and any unscoped absence entries; this wrapper does not manufacture project grants or invoke that review.

The immutable `CredentialRecoveryCheckpointStageResult` binds the configured authority identity, accepted checkpoint and sequence, original staging plan, source set and actual completion receipt. `CheckpointReadLeaseRetainedDuringStaging` and `InactiveRecoveryHold` are true. `NormalVaultUsable`, `PromotionAuthorized`, `NamespaceAdopted`, `ActivationPerformed`, `SourceHostFenced`, `ExternalExecutionAuthorized`, `KeyRetirementAuthorized`, `IndependentKeyBackupVerified`, `CustomerReviewAdmissionPerformed` and `ProductionRecoveryQualified` are false; `IndependentBackupCoverage` remains `NotAssessed`. Its digest binds these claims and the exact checkpoint and stage receipt commitments.

The shared lease gives a local observation interval, not a perpetual latest-state guarantee. A new checkpoint can be accepted immediately after release. A later promotion operation would require its own current checkpoint check, explicit authority, fresh destination and inactive custody policy. An earlier `HeldStageVerified` result has `PromotionAuthorized=false` and is never treated as a promotion permit here.

Cancellation and failures retain the inner executor's semantics. Before fresh reservation, refused inputs, key failures or elapsed validity do not create a stage. After reservation, the original executor retains the owned partial stage and returns an opaque outcome-unknown error; the wrapper does not repair, adopt or delete it. If the inner executor has returned a completion receipt but the wrapper's final checkpoint check or cancellation check fails, it returns `credential-recovery-checkpoint-stage-outcome-unknown`: a complete held stage can exist without a successful wrapper result. Do not blindly retry the same destination or infer no output from an exception.

The inner operation keeps its cooperative 20-second deadline. Cancellation cannot detach an uncooperative key provider: the task and checkpoint read lease remain held until the actual dependency returns, after which cancellation prevents success. No database transaction spans these waits. Same-owner or administrator bypass, rollback of both the set and its authority directory, trusted higher ancestors, independent key-backup coverage, organizational custody and production recovery qualification remain outside this local profile.

The native Windows synthetic integration tests cover current weak and strong source namespaces for both pipeline providers, expired and revoked profiles, empty sets and committed absence, stale valid selections, exact identity and signer pins, concurrent append refusal across source and destination waits, cooperative and uncooperative cancellation, destination and source key failures, expiry before publication, retained partial output after reservation, final checkpoint tamper detection and staging after the original live namespaces have been moved. They use generated keys and disposable private roots; no real credential caches, live pipelines, cell activation or Azure deployments are involved.
