# Workload naming binding review

4 October 2026. Source review for N1/N3, updated after the first integration group. **Private Storage, Key Vault and Observability now have optional typed standard-v2 bindings**, compiled across all four environments alongside legacy parameters. Their workload drafts enumerate reviewed owned components; principal-dependent RBAC identities remain unresolved. Existing defaults are retained. The other six rows below remain integration requirements. Full qualification also requires frozen Preview/Deploy bindings and live acceptance; local compilation alone does not complete N3.

All nine [registered compositions](../../config/workloads.json) use subscription stack wrappers that create a dedicated resource group. [The existing stack adapter](../../scripts/stack-service-common.ps1) uses subscription-scoped Deployment Stacks. The new draft registry therefore reserves both identities at subscription scope. Template Spec publication remains a separate shared platform concern, not a per-instance rename.

## Blocking design findings

1. Generic endpoint roles such as `blob` collide when two accounts in one group both have a blob endpoint. Add reviewed owner/service roles to the policy and golden plans; component keys alone disambiguate global hashes, not current scoped names. Never fix this by silently generating random suffixes.
2. Hosting plans, access connectors, alerts, node/managed groups and inline children still derive names inside modules. Concrete module parameters and output/reference changes must land together; a catalog-level preview alone would be inaccurate.
3. GUID children, storage/application contracts and platform references cannot all use the same convention. Names shown in proposed inventory must carry their classification and owning scope.
4. The first draft-instance contract reserves only RG/stack names. It does not enumerate workload resources, validate existing Azure ownership or qualify a deployment. N1/N2 remain in progress until the full source-to-request bindings and compatibility checks land.

Acceptance for each composition: resolve every included convention resource, explicitly mark excluded/unknown/service-assigned resources, compile both profiles, compare legacy output unchanged, verify nested reference IDs/settings and output names, and test repeated resources plus maximum input lengths. Then freeze the same parameter/name plan in Preview and Deploy before portal submission is enabled. [Full implementation plan](stack-naming-and-resource-previews.md).
