# Workload naming binding review

5 October 2026. All nine compositions have optional typed standard-v2 bindings, with nine stacks and 36 standard/legacy parameter pairs compiled locally. Owned network/subnet/DNS-link, hosting-plan, identity and managed-group bindings are included. Application children, exact shared references and provider-required names remain exceptions. The table records the binding responsibilities now implemented; live runtime/What-If qualification remains outstanding. Named drafts can use frozen Preview only; Deploy remains blocked.

All nine [registered compositions](../../config/workloads.json) use subscription stack wrappers that create a dedicated resource group. [The existing stack adapter](../../scripts/stack-service-common.ps1) uses subscription-scoped Deployment Stacks. The new draft registry therefore reserves both identities at subscription scope. Template Spec publication remains a separate shared platform concern, not a per-instance rename.

## Blocking design findings

1. Generic endpoint roles such as `blob` collide when two accounts in one group both have a blob endpoint. Owner/service roles are now present in the policy and golden plans; component keys alone disambiguate global hashes, not current scoped names. Never fix this by silently generating random suffixes.
2. Hosting plans, access connectors, alerts, node/managed groups and owned subnet/link names now have concrete parameters; legacy derivation remains the default. Reference/settings changes are in the same compositions.
3. GUID children, storage/application contracts and platform references cannot all use the same convention. Names shown in proposed inventory must carry their classification and owning scope.
4. The first draft-instance contract reserves only RG/stack names. It does not enumerate workload resources, validate existing Azure ownership or qualify a deployment. N1/N2 remain in progress until the full source-to-request bindings and compatibility checks land.

Acceptance for each composition: resolve every included convention resource, explicitly mark excluded/unknown/service-assigned resources, compile both profiles, compare legacy output unchanged, verify nested reference IDs/settings and output names, and test repeated resources plus maximum input lengths. Frozen named Preview is implemented. The remaining Deploy path must use the same reviewed map and qualify migration before named deployment submission is enabled.
