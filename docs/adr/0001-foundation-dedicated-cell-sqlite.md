# ADR 0001: first disconnected foundation uses a dedicated SQLite cell

Revision 23 appends schema v9 for [separate scoped recovery review](../foundation-scoped-recovery-review.md). Its target binds completed destination proof/core commitments and the full present-plus-absence scope union. Immutable requests/approvals/admissions and uncertain outcomes remain separate from v1 review tables. Fresh/upgrade/backup/restore tests use disposable cells; migration text and checksums 1–8 are frozen. Existing customer databases are not migrated by qualification.

Revision 19 appends schema v8 for [durable recovery-stage review](../foundation-credential-recovery-review.md). A bounded complete scope set, separate human approval and one-use admission bridge SQLite authorization to guarded read-only ciphertext verification. No database transaction spans a key-provider await. Restore quarantines unfinished review authority; credential activation and coordinated cutover remain unimplemented.

Date: 24 October 2026. Status: implemented for local disconnected qualification; production backend acceptance remains open.

The release architecture proposed SQL Server but did not establish a supported native SQL Server environment on this ARM64 workstation. The first executable foundation uses Microsoft.Data.Sqlite 10.0.10 with a separately bound database for each CustomerId/CellId. This allows real transactions, concurrency, crash recovery, append-only audit interfaces, durable leases and restoration tests without deploying a database or cloud resource. It is an explicit backend decision, not an in-memory substitute or a SQL Server qualification result.

SQLite runs with foreign keys, WAL and synchronous FULL. Intent, approval, outbox and audit writes use transactions; workers claim using immediate transactions and fenced leases. Connection generations, policy/membership versions and immutable plan digests are checked before dispatch. Database metadata rejects another customer/cell binding. Artifact bytes and SHA-256 digests share the cell database. Filesystem links are rejected. Database files must remain on a trusted local volume with owner-only OS access; SQLite is not encrypted by this implementation. Never put tokens or secret values in domain JSON. A filesystem administrator can bypass or rewrite this boundary, including audit triggers and hashes; externally anchored/WORM audit export remains a production requirement.

NuGet auditing remains enabled. The transitive SQLitePCLRaw.lib.e_sqlite3 2.1.11 dependency was rejected by the advisory check and replaced by a direct SQLitePCLRaw.bundle_e_sqlite3 3.0.5 reference, which supplies SQLite 3.53.4. The relevant [reviewed advisory](https://github.com/advisories/GHSA-2m69-gcr7-jv3q) identifies the old native package as affected. The new native SQLite package declares public-domain licensing; SQLitePCLRaw is Apache-2.0. Commercial redistribution still needs the release's complete dependency/license review.

The supported first topology is one local API host and independently owned workers per customer cell on the same trusted local machine. Tests exercise actual competing processes, crashes around dispatch, fenced leases, duplicates, audit/artifact integrity and online snapshots against this backend. They do not establish a multi-host cluster, shared multi-customer database, measured production SLO, network-filesystem safety, encryption-at-rest solution or SQL Server compatibility. Continued implementation supports schema v9 with additive transactional upgrades, immutable history/checksums and preflight integrity/guard checks; frozen earlier migration text/checksums remain unchanged. V5 assigns persistent instance identities and rotates them on restore. V6 adds separately approved credential-maintenance records with one-use admission and uncertain outcomes; it does not couple filesystem publication atomically to SQLite. V7 appends independently reviewed current-publication observation receipts while preserving the original uncertain execution; restore quarantines unfinished reviews without consulting custody files. [Local activation leases](../foundation-cell-activation.md) coordinate participating API/worker lifetimes against a separately protected authority root; they do not protect against an OS administrator or a cloned authority. Required-mode runtimes preflight existing state read-only and never provision, activate or upgrade it. Reviewed configuration/entitlements, paged exports, temporary access, lifecycle, signed audit/backups and optional loopback TLS extend the original slice; encryption-at-rest and independent backup/signer custody remain production requirements.

Before production, select and qualify the supported backend and backup policy against measured load, fault/recovery and security objectives. SQL Server needs its own adapter, migrations, transactional/concurrency tests and supported x64 runtime. Do not transfer SQLite test counts to that backend.
